### 2025-01-17: UX Proposal Patterns for Output-Focused Features

Completed UX companion doc for job output dashboard (`docs/proposals/job-output-dashboard-ux.md`). Key learnings:

**Feed vs. Detail patterns:**
- **Feed UI** (unified timeline of outputs) wins for demo and operator personas — scan multiple jobs in one screen, filter by status/job/date.
- **Detail UI** (per-job deep dive) wins for investigator persona — compare outputs over time for a single job.
- **Hybrid approach:** Build both. Feed as primary entry (new sidebar page), Detail as tab on existing JobDetail page. Low implementation cost, serves all personas.

**Markdown rendering is a UX requirement:**
- For content-first features (job outputs, reports), rendering markdown as `<pre>` blocks kills readability.
- MudBlazor doesn't include a markdown component — wrap `Markdig` (BSD license, widely used).
- Create reusable `MarkdownView.razor` component with sanitization (prevent XSS via Markdig's `HtmlRenderer`).

**MudBlazor component selection for feeds:**
- `MudCard` for output items — better than `MudList` (no built-in badge placement) or `MudExpansionPanels` (too hierarchical).
- `MudSelect` for filters — more intuitive than `MudChip` (read-only by default).
- Avoid `MudTimeline` for feeds — implies linear storytelling, not reverse-chronological scanning.

**Wireframing in ASCII:**
- Code-block wireframes (box-drawing chars) communicate layout faster than prose for async reviews.
- Always show 2-3 example items with realistic content (not "Lorem ipsum") — helps stakeholders spot UX issues.

**Persona-driven concept evaluation:**
- Define 3-4 personas upfront (Demo Presenter, Operator, Investigator, Casual User) with distinct goals/pain points.
- Evaluate each UX concept against all personas — avoid designing for only one use case.
- The "Demo Presenter" persona is unique to Bruno's conference context — most apps don't have this constraint, but OpenClawNet does. Factor it in.

### 2025-04-23: Post-creation navigation pattern (Job Templates)

Implemented auto-navigation after successfully creating a resource from a template:
- **Pattern**: After `CreateAsync` succeeds in `UseTemplate` method, immediately call `Navigation.NavigateTo($"/jobs/{created.Id}")` to take the user to the detail page.
- **Rationale**: Eliminates the need for inline success alerts and reduces friction. The user goes directly to the new resource page where they can take next actions (Run Now, Start, Cancel).
- **Error handling**: Keep error alerts on the same page so users see failure messages without losing context.
- **Loading state**: The loading spinner remains visible on the clicked button until navigation occurs, providing visual feedback during the async operation.

**Reusable pattern**: This "create-and-go" flow works well for any template-based or wizard-style creation UX where the immediate next step is to interact with the newly created resource.

### 2025-04-21: Tool approval flow architecture and type mismatch bug fix

**Tool approval flow (Wave 4 — NDJSON streaming):**

1. **Runtime emits approval request**: `DefaultAgentRuntime` (line ~480-494) generates a fresh `Guid` requestId, registers it with `IToolApprovalCoordinator.RequestApprovalAsync()`, and yields an `AgentStreamEvent` with type `ToolApprovalRequest` containing the requestId.

2. **Gateway streams to client**: `ChatStreamEndpoints.MapChatStreamEndpoints` (line ~259-267) maps `AgentStreamEventType.ToolApprovalRequest` to NDJSON type `"tool_approval"` and writes `ChatStreamEvent` with `RequestId` (Guid) to the response stream.

3. **Client displays approval UI**: `Chat.razor` (line ~508-521) receives the `"tool_approval"` event, stores it in `PendingApproval`, and renders `ToolApprovalCard` with Approve/Deny buttons.

4. **User clicks Approve/Deny**: `ToolApprovalCard.razor` invokes `OnApprove` or `OnDeny` EventCallback, which calls `Chat.razor.SubmitToolDecisionAsync` (line ~236-264).

5. **Client POSTs decision**: `SubmitToolDecisionAsync` sends `POST /api/chat/tool-approval` with JSON body `{ requestId: Guid, approved: bool, rememberForSession: bool }`.

6. **Gateway resolves request**: `ToolApprovalEndpoints.MapToolApprovalEndpoints` (line ~21-48) receives the POST, validates the requestId, and calls `IToolApprovalCoordinator.TryResolve()`.

7. **Coordinator completes Task**: `ToolApprovalCoordinator.TryResolve` (line ~58-71) pulls the pending `TaskCompletionSource<ApprovalDecision>` from a `ConcurrentDictionary<Guid, TCS>`, sets its result, and unblocks the runtime.

8. **Runtime proceeds**: The `await approvalTask` in `DefaultAgentRuntime` (line ~499) completes, and the tool executes or is skipped based on the decision.

**Root cause of "Approve button does nothing" bug:**

- **Type mismatch between client and server contract**: `PendingApprovalRequest` (Chat.razor line ~221-225) stored `RequestId` as `string`, but `ToolApprovalDecisionRequest` (ToolApprovalEndpoints.cs line ~55-60) expected `Guid`.
- When `SubmitToolDecisionAsync` called `PostAsJsonAsync`, it serialized requestId as a JSON string (e.g., `"3a7f..."`), but the server tried to deserialize it into a Guid property, causing a silent deserialization failure or 400 Bad Request.
- The `TryResolve` call never received a valid Guid, so the TaskCompletionSource remained incomplete, and the agent runtime hung indefinitely awaiting approval.

**Fix:**
- Changed `PendingApprovalRequest.RequestId` from `string` to `Guid` (Chat.razor line 222).
- Removed `.ToString()` call when constructing `PendingApprovalRequest` (Chat.razor line 516).
- Updated null/empty check from `string.IsNullOrEmpty(pending.RequestId)` to `pending.RequestId == Guid.Empty` (Chat.razor line 243).

**Files changed:**
- `src/OpenClawNet.Web/Components/Pages/Chat.razor` (3 edits: record definition, event handler, SubmitToolDecisionAsync guard)

### 2026-04-22: PR 2 — Tools, MCP Settings, Job Templates migrated to MudDataGrid

Three more pages off Bootstrap-table land. Same shape as the Tool Log pilot: `MudDataGrid<T>` + `ToolBarContent` density switch + `PagerContent` (10/25/50/100, default 25) + `FixedHeader`. Three commits, build green, tests at 525/527 baseline.

**ChildRowContent vs RowTemplate — ruling for the rest of the rollout:**

Default to `<ChildRowContent>`. It renders an expandable second row beneath the data row — the grid auto-adds the caret column, sort/filter/header chrome stay intact, and you get free state management for which rows are expanded. `<RowTemplate>` replaces the entire row's rendering, which forces you to hand-build sort/filter/select chrome and breaks `ShowColumnOptions`. Reach for `RowTemplate` only when the row layout is so custom the column model can't express it (no page in the current inventory needs that).

Applied this on MCP Settings (the post-Test result row was a colspan `<tr>` before — now it's `ChildRowContent`) and on Job Templates (prerequisites + prompt preview + secrets, all collapsed behind the caret instead of inline `<details>` stacks).

**MudDataGrid v9 quirks confirmed beyond the pilot:**

- `<TemplateColumn>` (no `Property`) is the right answer for purely-derived/action cells. Set `Sortable="false" Filterable="false"` so the header doesn't grow useless icons. `CellClass="text-end"` works for right-aligning action buttons.
- For columns where you want sort but the natural property order is nonsense (e.g. MCP status badges), use `<TemplateColumn ... SortBy="x => x.Enabled ? ... : ...">` with an int expression. Cleaner than projecting a synthetic prop on the DTO.
- `MudChip` with `Color="Color.Default" Variant="Variant.Outlined"` is the closest match to Bootstrap's `badge bg-light text-dark border`. Use `Color.Secondary` filled for `bg-secondary`.
- `data-testid` survives fine on inner elements inside a `CellTemplate` — no need to put it on the row itself (and you can't easily — MudDataGrid doesn't expose a per-row attribute hook).
- Card-grid → DataGrid is a legit conversion path. Job Templates was a 2-col card grid; flattening it to a table with ChildRowContent for the long-form bits made the page noticeably easier to scan.

**Migration pattern (Bootstrap table → MudDataGrid), now reusable:**

1. Identify the data source list `_items` and any per-row lookup dictionaries (e.g. `_results`, `_lastTest`) — those stay; only the rendering layer changes.
2. Add `private bool _dense = true;` to `@code`.
3. Replace `<table>` with `<MudDataGrid T="..." Items="..." Dense="_dense" Hover Striped Filterable SortMode="SortMode.Single" ShowColumnOptions FixedHeader Height="70vh" Elevation="0">`.
4. Add `<ToolBarContent>` with count + `<MudSwitch T="bool">` density toggle.
5. For each `<th>`: use `<PropertyColumn Property="x => x.Foo" Title="...">` if it maps to a real property, `<TemplateColumn Title="..." Sortable="false" Filterable="false">` for derived/action columns. Wrap rich content in `<CellTemplate>`.
6. Move per-row sub-rows (colspan `<tr>`, inline `<details>`) into `<ChildRowContent>`.
7. Add `<PagerContent><MudDataGridPager T="..." PageSizeOptions="new[] { 10, 25, 50, 100 }" /></PagerContent>`.
8. Build → fix any CS0411 from generic `MudChip`/`MudSwitch` (always specify `T=`).
9. Run unit tests with `--no-build`; baseline is 525/527.

Captured the migration pattern in `.squad/skills/blazor-table-mudblazor-migration/SKILL.md` and the ChildRowContent ruling in `.squad/decisions/inbox/helly-mudblazor-pr2.md` for PR 3 onwards (Agent Profiles + Model Providers).

**Playwright capture pattern for Blazor Server (.NET 10) — what worked:**

The `playwright` MCP server defaults to `--browser chrome` and fails on machines without Google Chrome installed. `playwright install chrome` requires admin privileges. Workaround: install **chromium** instead (`playwright install chromium` — works without admin) and either reconfigure the MCP with `--browser chromium` or bypass the MCP entirely.

This session bypassed the MCP because mcp_reload didn't recover the `playwright` connection after a config change. Used the `playwright` npm package directly via Node:

```js
const { chromium } = require('playwright');
const browser = await chromium.launch({ headless: true });
const ctx = await browser.newContext({ viewport: { width: 1440, height: 900 } });
const page = await ctx.newPage();
await page.goto(url, { waitUntil: 'domcontentloaded' });
await page.waitForTimeout(15000);  // crucial for Blazor Server SignalR re-render
await page.screenshot({ path: absoluteOutputPath, fullPage: false });
```

**Blazor Server SignalR gotcha:** `waitUntil: 'networkidle'` is *not* enough. The page prerenders with `_loading=true` (e.g. `Loading tools…` alert), then SignalR connects, then `OnInitializedAsync` runs again on the interactive circuit and re-renders with data. `networkidle` fires before SignalR's long-lived connection settles. Sleep 10–15s after navigation and additionally poll for the loading text to disappear via `page.waitForFunction((txt) => !document.body.innerText.includes(txt), 'Loading...')`. If the page is still in loading state after 60s, suspect a real circuit error — wire up `page.on('console', ...)` and `page.on('pageerror', ...)` to confirm.

### 2026-04-22: Tools page circuit crash — root cause + class-of-bug fix

**Bug:** PR 2 commit `373dda3` (Tools → MudDataGrid) shipped a page that threw an unhandled Blazor circuit exception on first load. Symptom: `Loading tools…` placeholder, then `An unhandled error has occurred. Reload`. Three other migrated pages (Tool Log, MCP Settings, Job Templates) appeared to work — but only because their grids didn't render in my smoke tests (Tool Log was empty; MCP/Job Templates I never visited with seeded data). MCP Settings reproduced the same exception once I navigated to it with the bug still in.

**Root cause (1 sentence):** `MainLayout.razor` declared `MudThemeProvider`/`MudPopoverProvider`/`MudDialogProvider`/`MudSnackbarProvider` without an explicit `@rendermode`, so they inherited the layout's static rendering and the popover service never initialized in the interactive circuit — `MudDataGrid`'s column-options popover then threw `InvalidOperationException: Missing <MudPopoverProvider />` from `OnInitializedAsync`.

**Fix:** tag each provider with `@rendermode="InteractiveServer"` (4-line change in `MainLayout.razor`). Verified in `aspire otel logs web --severity Error` (clean) and via Playwright snapshot of `/tools` showing all 14 tools rendered with sort/filter/page chrome intact.

**Gotcha I missed in PR 2:** I declared each migrated page green based on Playwright capture against an *empty* page (Tool Log had no executions; I never seeded MCP servers or Job Templates rows during verification). Empty-state pages skip the `MudDataGrid` render entirely (`@if (_items.Count == 0)`) so the popover code path never runs. Tools is the only page that always has data on a fresh install (the registered tool catalog), which is why it was the first to surface.

**Discovery path that worked:**
1. `aspire describe` → see all resources, find web's https URL.
2. `aspire otel logs web --severity Error -n 50 --format Json` → captured the actual `exception.type` + `exception.stacktrace` directly from the dashboard telemetry. Much faster than enabling `DetailedErrors` and re-binding to a port. **Use this first** for any future Blazor circuit exception investigation.
3. Compared providers in `MainLayout.razor` against MudBlazor docs for Blazor Web Apps with per-page render mode → confirmed missing `@rendermode`.

**Checklist for PR 3 (Agent Profiles + Model Providers) so this class of bug doesn't reappear:**
- [ ] Before declaring a migrated page green, ensure the data source has ≥1 row at test time. Seed if necessary.
- [ ] After navigating, immediately run `aspire otel logs web --severity Error -n 20` — circuit exceptions are silent in the browser unless `DetailedErrors=true`.
- [ ] Sanity-check `MainLayout.razor` still has `@rendermode="InteractiveServer"` on all four MudBlazor providers; don't let a future "tidy up" strip them.
- [ ] Avoid the temptation to declare success based on `_items.Count == 0` empty-state markup alone — it's not a real exercise of the grid.
- [ ] If you add a new layout (e.g. for Settings sub-pages), the same providers + rendermode tagging must be replicated, or those sub-pages must inherit `MainLayout`.

### Learnings

**ServerData in MudBlazor v9 — the signature is `Func<GridState<T>, CancellationToken, Task<GridData<T>>>`.** Skipping the `CancellationToken` parameter compiles cleanly in your method definition but the Razor source generator emits an explicit overload mismatch at the `ServerData=` attribute (`error CS0123: No overload for 'LoadGridDataAsync' matches delegate`). First failure of PR 4. Fix: always declare the second parameter, even if you ignore it. Update the skill so the next person hits the working signature first try.

**ServerData over an in-memory list is a legitimate pattern when the API has no paging.** The Gateway `GET /api/sessions` and the run-events endpoint both return the full list. We still load once into `_sessions` / `_events`, but route paging + sort + filter through the grid's GridState and only render the visible page. Net win: less DOM weight, sort/filter handled by the grid, and a clean upgrade path the day the Gateway adds `?skip=&take=`.

**External filter chrome + ServerData = `_grid.ReloadServerData()`.** Keep `@ref="_grid"` on the MudDataGrid, then any time outside-the-grid state changes (search box typed, filter chip toggled, bulk delete completes, inline rename committed), call `ReloadServerData()`. Without the explicit reload the grid keeps showing the stale page.

**Bulk-selection toolbar + per-row checkbox: keep the manual pattern.** Tools/MCP/JobTemplates didn't have selection — but Agent Profiles, Model Providers, and Sessions do. MudDataGrid has built-in `MultiSelection`, but flipping to that would have meant rewriting the toolbar's "Set as Default" / "Delete N selected" / "Deselect all" handlers and breaking any callers of the existing `_selected` state. Cheaper: keep the existing `_selected` HashSet + `ToggleItem` / `ToggleSelectAll` / `AllSelected` and implement them as a `TemplateColumn` with a `HeaderTemplate` for select-all and a `CellTemplate` for the row checkbox. Zero changes to the bulk handlers.

**Sub-row content with `MudCard Class="pa-2 mud-background-gray"`** continues to be the right pattern (matches Tools.razor / Job Templates / MCP Settings). It gives the muted-background "second row" look the old colspan `<tr>` had, without fighting the grid's column model.

**`RowClass` for status-coloured rows is a footgun in v9.** JobRunEvents previously coloured the failed-event row red. I dropped that — the `Color.Error` chip on the Kind column conveys the same signal and `RowClass` on a function callback would have re-renedered every row on every state change. Net: cleaner rendering and the failure is still visually obvious.
